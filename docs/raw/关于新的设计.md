# 一、先看看当前代码实际上是什么

当前核心路径大概是：

```text
FastMCP Server
    ↓ 创建并拥有
IPythonMCPAdapter
    ↓ 拥有
KernelSession
    ↓ 拥有/引用
KernelRuntime
    ↓ 启动
IPython Kernel 子进程
```

执行过程是：

```text
MCP run_cell
    ↓
IPythonMCPAdapter.run_cell()
    ↓
解析 # loommux 指令、转换 Apply Patch 字符串
    ↓
创建 Execution
    ↓
KernelSession.submit()
    ↓
Jupyter ZMQ
    ↓
IPython Kernel
    ↓
IOPub collector 后台线程
    ↓
更新 Execution / ExecutionLogs
    ↓
Adapter 生成 dict
    ↓
MCP presentation / ToolResult
```

这条链路其实已经能工作，而且职责并非完全混乱。

## 目前值得保留的部分

### 1. Kernel 启动层已经有不错的雏形

`coding_agent_kernel.py` 里的 `KernelLaunch` 清楚地描述了：

- Python 解释器；
- Kernel 启动命令；
- 子进程环境；
- 私有 IPython/Jupyter 配置目录；
- connection file；
- private runtime root。

`kernel_runtime.py` 又把 Jupyter `KernelManager`、启动、interrupt、shutdown 和 Windows Job Object 包起来了。

这个方向是对的：**操作系统进程与 Jupyter 连接细节不应该泄漏到控制面上层。**

### 2. Execution 和输出日志已经形成独立概念

`execution.py` 与 `output_log.py` 已经提供了：

- Loommux 自己的 execution 编号；
- `running/completed/error/interrupted/killed` 状态；
- stdout、stderr、result、traceback、combined；
- 行范围读取；
- 搜索；
- 长输出省略策略；
- 展示事件；
- ANSI/terminal control normalization。

尤其是区分：

```text
Loommux execution N
!=
IPython kernel-local execution_count
```

这是很重要的设计，不应该丢掉。

### 3. MCP 的展示层已经有一定隔离

`presentation.py` 和 `mcp_result_policy.py` 已经在做：

- 核心状态到模型可读文本的投影；
- MCP `TextContent` / `ImageContent`；
- 图像大小和数量限制；
- content 与 structured content 的差异。

这说明现有设计并不是完全把 MCP 散落在每一个角落，而是已经有适配层意识。

# 二、问题不在“小零件”，而在“谁拥有谁”

最关键的一行其实在 `mcp_server_factory.py`：

```python
adapter = IPythonMCPAdapter()
```

随后 FastMCP lifespan 启动它、关闭它。也就是说：

> **MCP Server 是组合根，是最上层所有者；Kernel 控制系统是 MCP Server 的内部实现。**

与此同时，`IPythonMCPAdapter` 的类注释直接写着：

> Owns the server-local execution sequence and one persistent kernel.

这个类当前同时拥有：

- workspace；
- Python 路径；
- Kernel；
- execution registry；
- execution 序列；
- current/recent execution；
- busy 仲裁；
- restart/interrupt；
- 输出选择；
- MCP 风格的字典错误表面；
- 一部分请求预处理策略。

所以它虽然叫 **Adapter**，实际上却是：

```text
KernelController
+ ExecutionRepository
+ SessionLifecycle
+ RequestService
+ 一部分 MCP Adapter
```

这就是你感到奇怪的根本原因：**名义上它是适配器，实际上它是整个业务核心。**

# 四、我想象中的理想 IPython 使用体验

我认为最终应该能这样用：

```python
from loommux import Loommux

mux = Loommux()

research = mux.start_kernel(
    "research",
    cwd="/home/me/research",
)

project = mux.start_kernel(
    "project",
    cwd="/home/me/project",
)
```

这里：

- `mux` 是整个本地控制系统；
- `research` 是一个 Kernel 对象；
- `project` 是另一个 Kernel 对象；
- 每个 Kernel 有独立 namespace、进程、执行序列和历史记录；
- 两个 Kernel 可以并行运行。

然后：

```python
execution = research.submit("""
import pandas as pd
df = pd.read_csv("data.csv")
df.describe()
""")
```

`submit()` 应该快速返回，不等执行完成。

```python
execution
```

IPython 中可以显示成：

```text
<Execution research:1 running>
```

继续：

```python
execution.status()
execution.wait(timeout=30)
execution.output.read()
execution.output.search("warning|error", regex=True)
```

也可以提供方便的短任务接口：

```python
execution = research.run("sum(range(100))", wait=10)
```

它仍然返回 `Execution`，只是附带一个初始等待窗口。

Kernel 自身还可以保留现有八项能力：

```python
research.run_cell(...)
research.status()
research.execution_status(...)
research.read_output(...)
research.search_output(...)
research.wait(...)
research.interrupt()
research.restart()
```

但是在 Python 场景中，更丝滑的方式应当是把操作挂在执行对象上：

```python
execution.status()
execution.wait()
execution.read_output()
execution.search_output()
```

也就是说：

- **八接口继续作为稳定的低层控制协议；**
- **对象式 API 成为 IPython 第一体验。**

还可以有：

```python
research.executions
research.current
research.recent
research[12]
```

例如：

```python
research[12].output.tail(20)
```

Kernel 间可以并行：

```python
a = research.submit("train_model()")
b = project.submit("run_tests()")

a.wait()
b.wait()
```

如果需要实时事件：

```python
for event in a.events():
    print(event)
```

异步场景则是：

```python
async for event in a.aevents():
    ...
```

这才像一个真正生长在 IPython 里的控制系统，而不只是把 MCP tool 手工换成 Python 方法。

# 五、Python 变量名和 Kernel 名称需要区分

你提到：

> 我用一个 Python 变量创建 Kernel 实例，那变量的名字就是这个 Kernel。

体验上完全可以这样理解：

```python
research = mux.start_kernel("research")
```

但库本身不应该尝试从赋值语句中猜出变量名 `research`。一个 Python 对象可能同时被多个变量引用：

```python
research = kernel
backup = kernel
kernels[0] = kernel
```

所以健康的设计是：

- Python 变量名由用户自由决定；
- Kernel 有明确、稳定的内部 `kernel_id`；
- 可以有显式的人类可读别名 `name="research"`；
- 名称用于展示和注册表查找，不作为绝对身份。

例如：

```python
research.id
# UUID 或稳定内部 ID

research.name
# "research"

mux["research"] is research
# True
```

这样变量体验很自然，身份语义又不会依赖 Python 作用域魔法。

# 六、我建议的所有权结构

我认为应该建立下面的所有权树：

```text
Loommux
├── BackgroundRuntime
├── KernelRegistry
├── Kernel("research")
│   ├── KernelController
│   ├── KernelDriver
│   ├── ExecutionStore
│   └── Output/Event Journal
└── Kernel("project")
    ├── KernelController
    ├── KernelDriver
    ├── ExecutionStore
    └── Output/Event Journal
```

具体来说：

## 1. `Loommux`

这是 Python 包的组合根和明确所有者。

它负责：

- 后台运行时；
- 多 Kernel 注册表；
- 创建、查找、关闭 Kernel；
- 进程退出时的统一清理；
- 可选的 MCP/HTTP adapter 创建。

例如：

```python
mux = Loommux()
mux.start_kernel("a")
mux.start_kernel("b")
mux.list_kernels()
mux.close()
```

它应该支持：

```python
with Loommux() as mux:
    kernel = mux.start_kernel("work")
```

不过在 IPython 里，跨多个 cell 使用 `with` 不方便，因此显式 `close()` 和 `atexit` 兜底也必须做好。

不能把正确清理依赖于 `__del__`。`__del__` 只适合最后兜底，不能成为生命周期契约。

## 2. `Kernel`

`Kernel` 是用户手里的公共对象，也就是你想绑定到变量的东西。

它不应该直接暴露 `BlockingKernelClient`，而是一个稳定 façade：

```python
kernel.submit(...)
kernel.run(...)
kernel.interrupt()
kernel.restart()
kernel.close()
kernel.status()
```

它可以持有对内部 supervisor/runtime 的引用，但用户不需要知道 ZMQ、线程或 event loop。

## 3. `KernelDriver`

这是现在 `KernelRuntime` 的演进版。

它只负责：

- 启动 Kernel 进程；
- 建立 Jupyter channels；
- 提交 execute request；
- interrupt；
- shutdown；
- Kernel 是否存活；
- connection/runtime root 的清理。

它**不负责 execution 编号、输出搜索、MCP 文本或业务状态选择**。

这样未来甚至可以出现别的 driver：

```text
LocalJupyterDriver
RemoteJupyterDriver
ExistingConnectionDriver
SSHKernelDriver
```

但这不是第一阶段必须实现的，只要边界允许即可。

## 4. `KernelController`

这是当前 `IPythonMCPAdapter` 真正的核心部分。

它负责：

- Kernel 状态机；
- 当前 execution；
- execution 分配；
- busy 策略；
- restart generation；
- Kernel event 与 Execution 的关联；
- 公开命令语义。

它不应该知道 FastMCP、`ToolResult`、`TextContent` 或 Chinese tool docstring。

## 5. `ExecutionStore`

每个 Kernel 应当有自己的 execution sequence：

```text
research:1
research:2
project:1
project:2
```

在单 Kernel 的 MCP adapter 中，仍然只暴露整数：

```text
execution = 1
```

在 Loommux 全局范围内，则使用复合身份：

```python
ExecutionRef(kernel_id=..., sequence=1)
```

Kernel restart 不重置 sequence，继续保持现有优秀语义。

## 6. `MCPKernelAdapter`

MCP 不再创建和拥有业务核心，而是绑定一个已经存在的 Kernel：

```python
adapter = MCPKernelAdapter(kernel)
mcp = create_mcp(adapter)
```

甚至可以简化为：

```python
mcp = create_mcp(kernel)
```

只要 `Kernel` 实现一个清楚的控制协议即可：

```python
class KernelControl(Protocol):
    def run_cell(...): ...
    def status(...): ...
    def execution_status(...): ...
    ...
```

MCP adapter 的职责只是：

- 解析 MCP 输入；
- 将 MCP 请求映射到 Kernel 命令；
- 将 typed result 映射成 `ToolResult`；
- 应用图像交付限制；
- 应用 coding-agent source directive；
- 把异常转换为 MCP 状态。

这才是真正意义上的适配器。

# 七、主事件循环、线程还是独立进程？

这是这次设计最关键的技术选择之一。

我的建议是：

> **核心内部采用一个专用后台 asyncio event loop 线程；对 IPython 默认暴露同步对象式 API，同时提供 async API。**

结构是：

```text
IPython 主线程
    │
    │ 调用同步 API
    ▼
Loommux public facade
    │
    │ thread-safe command / Future
    ▼
Loommux 后台 runtime 线程
    └── 一个 asyncio event loop
          ├── Kernel A event pump
          ├── Kernel B event pump
          ├── Kernel C event pump
          └── 生命周期与状态命令
```

## 为什么不直接占用当前 IPython 的 event loop？

因为 IPython 的运行环境不统一：

- 终端 IPython 可能没有持续运行的用户级 asyncio loop；
- Jupyter/IPykernel 通常已经有 event loop；
- 某些环境支持 top-level await；
- 在已有 loop 中调用 `asyncio.run()` 会失败；
- 如果 Loommux 把用户的 REPL loop 当作内部生命周期所有者，退出、异常和重入会很难处理。

专用 runtime thread 能提供稳定边界：

- 用户不需要先学会 event loop 管理；
- Jupyter 和终端 IPython 体验一致；
- 多 Kernel 的 IOPub 可以并发收取；
- 同步 API 不会污染内部异步实现；
- MCP HTTP 自己的 async loop 也不会和核心打架。

当前安装的 `jupyter_client 8.8.0` 已经提供 `AsyncKernelManager` 和 `AsyncKernelClient`，所以这条技术路线是成立的。

## 为什么不继续每个 Kernel 一个 collector 线程？

当前 `KernelSession` 的做法是每个 Kernel 启一个：

```python
threading.Thread(target=self._collect_iopub, ...)
```

对于一两个 Kernel，这是完全可用的，甚至可以作为重构第一阶段的过渡实现。

但长期看，一个 asyncio runtime 更适合多 Kernel：

- 不需要每个 Kernel 一个永久 collector 线程；
- 命令和事件可以在同一个 runtime 所有权域中处理；
- 状态变更天然串行；
- 可以大幅减少锁；
- 更容易实现事件订阅和异步等待；
- 更容易避免读写 `Execution` 时的并发不一致。

所以我不建议马上为了“纯异步”推翻一切，但最终目标应当是后台 async runtime。

## 是否应该变成独立 daemon 进程？

第一阶段不建议。

当你在 IPython 中写：

```python
mux = Loommux()
```

健康语义应当是：

> 当前 IPython 进程托管 Loommux 控制面；Loommux 又拥有多个 Kernel 子进程。

当这个 IPython 退出时，Loommux 应关闭其 Kernel。

如果以后希望：

- 关闭控制 IPython 后 Kernel 继续运行；
- 另一个客户端重新连接；
- 跨进程共享；
- Kernel 状态持久化；
- 多个前端同时管理；

那已经是另一种产品：

```text
loommuxd 外部守护进程
+ Python client
+ MCP adapter
+ 可重连协议
```

这个可以成为第二层部署模式，但千万不要在第一代核心里把“进程内对象”和“远程 daemon proxy”混成一套隐式语义。

# 八、当前并发和数据所有权存在的隐患

现在的代码在单 Kernel、轻并发下可以运行，但扩展到多 Kernel 前必须处理几个问题。

## 1. `current_execution` 有两个所有者

当前：

- `IPythonMCPAdapter.current_execution`
- `KernelSession.current_execution`

都记录当前执行。

完成时由 KernelSession 清自己，再通过 callback 清 Adapter。

这属于重复状态源。只要未来加入：

- Kernel 意外退出；
- 并发 restart；
- 多 Kernel；
- 事件丢失；
- shutdown race；

两个字段就可能不一致。

新设计中，`current_execution` 只能由 `KernelController` 的状态机拥有。Driver 只报告事件，不持有业务意义上的 current execution。

## 2. `Execution` 被跨线程直接修改和读取

IOPub collector 线程会调用：

```python
execution.append_stdout(...)
execution.record_error(...)
execution.finish()
```

与此同时，MCP tool 线程可能调用：

```python
execution.snapshot()
execution.logs.read()
execution.logs.search()
```

目前 `Execution` 和 `LineLog` 没有自己的同步边界。

CPython 的 GIL 不能保证多个关联字段形成一致快照。例如可能读到：

- status 已经 terminal；
- 但 completed_at 尚未写入；
- output string 与 line count 来自不同更新时刻；
- error 已写入但 traceback log 还未完整追加。

新架构中，最干净的方式不是给每个字段到处加锁，而是：

> **所有可变 Kernel/Execution 状态只在后台 runtime 线程中更新；外部只能请求不可变 snapshot。**

## 3. 同一数据被重复保存

当前 `Execution` 同时保存：

- `stdout` 字符串；
- `stderr` 字符串；
- `result_text`；
- `error`；
- `ExecutionLogs` 中的五份流投影；
- `presentation` 中再次出现的文本片段。

这会带来：

- 内存重复；
- 多处更新；
- 顺序一致性依赖调用顺序；
- 未来扩展 output event 时容易漏一个投影。

我建议把核心事实改成一个 append-only event journal：

```text
StreamEvent(stdout, text)
StreamEvent(stderr, text)
DisplayEvent(mime_bundle, metadata)
ErrorEvent(error)
ExecuteInputEvent(kernel_count)
KernelIdleEvent
```

然后由 reducer 维护：

- lifecycle state；
- text transcript；
- stream index；
- presentation order。

不一定每次读取都从头重算，可以增量缓存，但必须明确：

> **事件序列是事实源，stdout/result/presentation 是投影，不是多个并列事实源。**

# 九、状态机需要正式设计

## Kernel 状态

建议至少有：

```text
NEW
STARTING
IDLE
BUSY
RESTARTING
STOPPING
STOPPED
FAILED
```

典型迁移：

```text
NEW -> STARTING -> IDLE
IDLE -> BUSY -> IDLE
IDLE/BUSY -> RESTARTING -> IDLE
ANY -> STOPPING -> STOPPED
STARTING/RESTARTING -> FAILED
```

Kernel 应有 `generation`：

```text
research generation 1
restart
research generation 2
```

Execution 记录所属 generation，以便诊断：

```python
execution.kernel_generation
```

## Execution 状态

建议比现在稍微完整一些：

```text
ACCEPTED
RUNNING
COMPLETED
ERROR
INTERRUPTED
KILLED
LOST
SUBMISSION_FAILED
```

这里需要区分：

- Python 抛出异常：`ERROR`
- 用户 interrupt，最终收到 `KeyboardInterrupt`：`INTERRUPTED`
- restart 主动终止：`KILLED`
- Kernel 意外死亡：`LOST`
- execute request 根本未成功提交：`SUBMISSION_FAILED`

当前实现把提交失败用 `record_error()` 记作普通 Python error，会混淆控制平面故障与被执行代码故障。

另外：

- `wait(timeout)` 超时不是 Execution 状态；
- `interrupt_sent` 是控制命令结果，不是最终状态；
- `restart` 必须终结旧 generation 的 active execution；
- historical execution 在 restart 后仍可读。

---

# 十、Python API 不应继续全部返回字典

当前 Adapter 返回：

```python
{
    "ok": True,
    "status": "completed",
    "execution": 1,
    ...
}
```

对 MCP 很合适，因为它天然需要可序列化结构；但对 Python/IPython 用户而言不够自然。

应该返回 typed objects：

```python
KernelStatus
ExecutionSnapshot
OutputSlice
SearchResult
InterruptResult
RestartResult
```

例如：

```python
status = research.status()
status.state
status.pid
status.current_execution
```

而不是：

```python
status["kernel_started"]
status["current_execution"]
```

控制面输入错误在 Python API 中应该倾向于异常：

```python
KernelBusyError
KernelClosedError
InvalidTimeoutError
ExecutionNotFoundError
```

但 Python 代码执行本身的异常不应默认让控制调用抛异常，因为那是 Execution 的合法终态：

```python
execution = kernel.run("1 / 0")
execution.state
# ERROR
```

如果用户想把远程 Python error 转成当前进程异常，可以显式：

```python
execution.result(raise_on_error=True)
```

MCP adapter 则捕获控制异常，转换回现有：

```json
{"ok": false, "status": "busy", ...}
```

这样 Python API 与 MCP API 都符合各自生态习惯。

---

# 十一、coding-agent 特性应该移出核心执行路径

目前 `adapter.run_cell()` 直接做：

1. `# loommux:` directive 扫描；
2. directive 删除；
3. Apply Patch literal 转换；
4. 执行提交。

这两类功能很有价值，但它们明显是 **coding-agent frontend policy**，不应该成为每次 Python API 执行的强制核心语义。

在 Python API 中，用户本来就可以写：

```python
kernel.run(
    source,
    wait=120,
    full_output=True,
)
```

不需要在源码里嵌入：

```python
# loommux: --wait 120 --full-output
```

所以应该设计一个 source preparation pipeline：

```python
SourceRequest
    ↓
SourceProcessor[]
    ↓
PreparedCell
```

MCP adapter 使用：

```text
LoommuxDirectiveProcessor
ApplyPatchLiteralProcessor
```

普通 Python API 默认使用：

```text
IdentityProcessor
```

或者用户明确选择：

```python
kernel.run_agent_cell(source)
```

这样：

- 核心 Kernel 不知道 Apply Patch；
- MCP 保持向后兼容；
- 以后可以添加别的 frontend policy；
- 普通 IPython source 不会被 coding-agent grammar 隐式改写。

同理，图像 Base64 限制属于 MCP 交付层，不属于 Execution 状态本身。

---

# 十二、IPython-first 还意味着启动策略需要分层

当前 coding-agent kernel 启动策略包括：

- 禁止 history；
- output cache 为 0；
- 禁用用户 profile；
- 关闭颜色；
- 不执行 `PYTHONSTARTUP`。

对于确定性 coding-agent 很合理，但如果 IPython 是第一场景，就不应该把它们全部硬编码成唯一 Kernel 语义。

建议引入：

```python
KernelPolicy.interactive()
KernelPolicy.agent()
```

例如：

## `interactive`

面向 IPython/Python 用户：

- 保留 IPython magics；
- 保留 top-level await；
- 允许合理的内存输入历史；
- 可选择启用 `Out[n]` cache；
- 默认仍不写用户磁盘历史，避免污染；
- rich display 完整保留。

## `agent`

面向现有 MCP：

- 禁止磁盘 history；
- cache size 0；
- 私有 profile；
- 无 terminal color；
- 规范化文本；
- 现有长输出策略；
- agent source processors。

默认 Python 包可以是 `interactive`，而 CLI：

```text
loommux
```

显式使用 `agent` policy，以保持当前 MCP 契约。

workspace 也类似：

- Python API 直接接收明确的 `cwd`；
- MCP host 才需要 resolver 和授权规则；
- resolver 不应该成为核心 Kernel 的唯一创建方式。

Python 用户还可以明确传解释器：

```python
mux.start_kernel(
    "py313",
    python="/path/to/python",
    cwd="...",
)
```

而 MCP CLI 为安全和确定性，仍然可以规定必须使用 `sys.executable`。

这就是“核心能力”和“宿主授权策略”的区别。

# 十三、`import loommux` 必须变得干净

当前 `src/loommux/__init__.py` 导入：

```python
from loommux.mcp_ipython_server import create_mcp, mcp
```

而 `mcp_ipython_server.py` 在模块级执行：

```python
mcp = create_mcp()
```

这意味着普通用户只要：

```python
import loommux
```

就会创建 FastMCP server object 和内部 Adapter 对象。虽然 lifespan 尚未启动 Kernel，但这仍然是错误的 Python library 边界：

- 导入核心包依赖 FastMCP；
- 导入时构造服务对象；
- MCP 概念污染顶层命名空间；
- 无 MCP 需求的用户仍加载 MCP 依赖链；
- 测试和插件环境容易出现隐式对象。

理想顶层应该只有：

```python
from loommux import Loommux, Kernel, Execution, KernelConfig
```

MCP 放到显式命名空间：

```python
from loommux.adapters.mcp import create_mcp
```

或：

```python
import loommux.mcp
```

控制台入口自己导入 MCP，不经过顶层包导出全局 `mcp`。

这一项我会把它列为重构第一批完成的事情。

# 十四、MCP 如何与多 Kernel 共存

你说“每一个 Kernel 都有八个函数”，我非常赞成。

最稳妥的模型是：

> 一个 MCP adapter 绑定一个 Kernel，继续暴露原来的八个 tools。

```python
research = mux.start_kernel("research")
research_mcp = create_mcp(research)
```

这样 MCP tool schema 完全不需要加 `kernel` 参数，已有客户端也最容易兼容。

如果希望一个 MCP endpoint 管理多个 Kernel，可以另做一种 adapter：

```text
LoommuxHubMCPAdapter
```

它可能有：

- `list_kernels`
- `create_kernel`
- `close_kernel`
- `select_kernel`

或者所有执行工具都增加 `kernel` 参数。

但我不建议一开始把这套管理协议塞进现有八工具。因为：

- 单 Kernel 控制协议已经很清晰；
- 多 Kernel 管理是另一个协议层；
- Python API 已经天然可以多 Kernel；
- MCP 是否需要动态创建 Kernel，应由安全模型决定。

所以应当是：

```text
Core：天然多 Kernel
Kernel MCP Adapter：绑定单 Kernel，八工具不变
Hub MCP Adapter：可选的多 Kernel 管理扩展
```

# 十六、推荐的迁移顺序

这次不要一口气把所有代码打散。我建议分七步。

## 第一阶段：先定义新的公共体验

先写 IPython-facing tests，例如：

```python
mux = Loommux()
kernel = mux.start_kernel("work", cwd=tmp_path)
execution = kernel.run("x = 40; x + 2")
assert execution.output_text == "Out[1]: 42\n"
```

以及多 Kernel：

```python
a = mux.start_kernel("a")
b = mux.start_kernel("b")

a.run("value = 1")
b.run("value = 2")

assert a.run("value").result_text == "1"
assert b.run("value").result_text == "2"
```

先决定体验，再动内部实现。

## 第二阶段：去掉顶层 MCP 副作用

让：

```python
import loommux
```

不创建 FastMCP 对象，不导入 MCP server graph。

## 第三阶段：从 Adapter 提取核心 Controller

先不改线程模型，只把：

```text
IPythonMCPAdapter
```

拆成：

```text
KernelController
MCPKernelAdapter
```

让现有八工具测试继续全部通过。

## 第四阶段：加入 `Loommux` 与多 Kernel registry

这一阶段甚至可以暂时继续使用“每个 Kernel 一个 collector thread”。

先把正确的对象关系立起来，别同时重写所有并发细节。

## 第五阶段：引入 typed Python API

加入：

- `Kernel`
- `Execution`
- snapshot dataclasses；
- Python exceptions；
- 对象式 output API。

MCP adapter 将 typed object 序列化回当前字典契约。

## 第六阶段：把内部可变状态迁到后台 async runtime

切换为：

- 一个专用 event-loop thread；
- 每个 Kernel 一个 event-pump task；
- runtime 内串行更新状态；
- 外部只读取 snapshot。

这是解决长期并发健康度的关键阶段。

## 第七阶段：拆出 agent policy

最后将：

- Loommux directives；
- Apply Patch literal；
- MCP presentation；
- 图像交付限制；
- workspace host resolver；

全部收敛到 adapter/policy 层。

此后核心才真正成为独立 Python 控制系统。

# 十七、最后给出一句最核心的设计原则

如果让我为新版 Loommux 写一句架构宪法，我会写：

> **Loommux core owns kernels and executions; frontends only borrow and present them.**

中文就是：

> **Kernel 和 Execution 由 Loommux 核心拥有；IPython、MCP、CLI、HTTP 只是操作和呈现这些对象的前端，任何前端都不能反过来定义核心生命周期。**

当前正好相反：

```text
MCP lifespan
    owns Adapter
        owns Kernel
```

新版应该是：

```text
Loommux
    owns Runtime
        owns Kernels
            own Executions

IPython facade ─┐
MCP adapter ────┼── borrow/control
HTTP adapter ───┤
CLI ────────────┘
```

# 我的最终判断

是的，这值得做一次比较大的核心重构，但不是“把所有文件推倒重写”。

更准确地说：

- **底层 Jupyter 启动和输出处理可以继承；**
- **现有八工具契约可以保留；**
- **现有黑盒测试是非常有价值的安全网；**
- **真正需要重建的是中间层：所有权、状态机、运行时和公共 API；**
- **MCP 要从主人降级为适配器；**
- **IPython/Python 对象式体验要提升为第一入口；**
- **多 Kernel 必须是核心天然能力，而不是 MCP Server 数量的副作用。**

而且我非常赞同你现在提出这个方向。代码再增长两三倍以后再动，成本会高很多；现在它“就那么点点”，正适合认真把骨架长正。

这轮我只做了阅读与设计分析，**没有修改任何文件**；另外当前仓库本身已有若干未提交的 workspace 配置与文档改动，我也没有碰它们。下一步如果正式开始，我建议先产出一份新的 **IPython-First Loommux Core Architecture Design**，把公共 API、所有权树、Kernel/Execution 状态机、线程模型和 MCP 适配边界写成事实源，然后再按上述阶段落代码。
